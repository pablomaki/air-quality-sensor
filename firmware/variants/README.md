# Build variants

One overlay plus one conf fragment per product variant, layered on top of
`prj.conf` and the board overlay rather than replacing them. Nothing in
`prj.conf` changes between variants.

## Why the overlay decides the sensors

Each `CONFIG_ENABLE_<sensor>` symbol depends on the matching devicetree node and
defaults to `y`:

```kconfig
config ENABLE_SHT4X
    bool "Enable SHT4X sensor"
    depends on DT_HAS_SENSIRION_SHT4X_ENABLED
    default y
```

`DT_HAS_SENSIRION_SHT4X_ENABLED` is generated by the build whenever a node has
`compatible = "sensirion,sht4x"` and `status = "okay"`. So enabling a node in the
variant overlay turns on the Zephyr driver *and* the application support for it,
with no Kconfig entry anywhere. The conf fragment carries only what the
devicetree cannot express - the BSEC licence path, product name, altitude,
timing.

If you ever want a fitted part deliberately switched off in one build, add
`CONFIG_ENABLE_<sensor>=n` to that variant's fragment. That works and is silent.
The reverse - `=y` for a part whose node is disabled - cannot force it on: the
`depends on` wins and Kconfig warns, naming the unsatisfied dependency.

## Building

`EXTRA_DTC_OVERLAY_FILE` and `EXTRA_CONF_FILE` are additive, so the base
`prj.conf` and board overlay still apply underneath:

```sh
west build -b xiao_ble/nrf52840/sense -d build/aqs_001 -- \
    -DEXTRA_DTC_OVERLAY_FILE=variants/aqs_001.overlay \
    -DEXTRA_CONF_FILE=variants/aqs_001.conf
```

Separate `-d` directories let the variants coexist without rebuilding each
other. To build them all:

```sh
for v in aqs_001 aqs_002 aqs_003; do
    west build -b xiao_ble/nrf52840/sense -d "build/$v" -- \
        -DEXTRA_DTC_OVERLAY_FILE="variants/$v.overlay" \
        -DEXTRA_CONF_FILE="variants/$v.conf" || break
done
```

In the nRF Connect extension, add one build configuration per variant and put
the two `-D` arguments in "Extra CMake arguments".

## Two one-time changes this needs

**1. Label the sensor nodes** in `boards/xiao_ble_nrf52840_sense.overlay`, so the
variant overlays can refer to them:

```dts
sht4x: sht4x@44  { ... };
sgp40: sgp40@59  { ... };
scd41: scd41@62  { ... };
bmp390: bmp390@77 { ... };
bme680: bme680@77 { ... };
```

Leave them all `status = "disabled"` there. The base overlay then describes what
the board *can* carry, and each variant says what is actually fitted. Building
without a variant gives a node with no sensors, which is a clearer default than
an arbitrary set.

**2. Delete the per-sensor lines from `prj.conf`**, so the devicetree defaults
win. Without this the shared baseline overrides every variant:

```
CONFIG_ENABLE_SHT4X=y     <- remove
CONFIG_ENABLE_SGP40=n     <- remove
CONFIG_ENABLE_SCD4X=y     <- remove
CONFIG_ENABLE_BMP390=n    <- remove
CONFIG_ENABLE_BME680=n    <- remove
```

Keep `CONFIG_ENABLE_EVENT_LED` - it has no devicetree node behind it, so it is a
plain application choice and belongs in the shared baseline.

## Adding a variant

1. Copy an overlay and set each of the five sensors to `okay` or `disabled`.
2. Copy a conf fragment only if the variant needs something beyond sensor
   selection.

Remember the BME680 and BMP390 share address 0x77 and cannot both be enabled.
